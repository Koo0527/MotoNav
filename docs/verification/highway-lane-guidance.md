# 高速车道显示修复

## 已确认的问题与修改

- 统一 iOS HUD 的 `NavigationReadout` 原先没有车道或路口图片，因此“完整导航提示”可见的数据未在统一页绘制。现在由现有 SDK 车道字符串生成官方车道图，接入统一 HUD；独立接收路口放大图 show/hide 回调。竖屏放在转向卡下，横屏放在旁边，并参与现有 HUD 高度测量。
- 圆屏地图页、纯导航页及地图 HUD 避让均用 `laneN > 0 && ringActive`。`ringActive` 仅在非直行且距转弯不超过 500 米时成立，导致高速提前车道提示被隐藏。三处统一改为根据已收到的车道数显示，SDK hide、导航清屏和巡航仍负责清除。
- 新图片回调使用现有 session generation 门控，过期会话不能显示或清除新会话图片。SDK 原生视图可能消费放大图并回调 nil，因此 nil 不作为 hide；显式 hide 和导航 reset 才清除。
- 手机图片使用完整 SDK 编码，不依赖旧版 BLE 车道编码的去重结果。圆屏继续用原 `#j`，不改变配对、NVS、校准或地图格式。

## 本轮未实现与实测边界

- 更新后用户模拟期间串口已记录 `LANE HUD visible=1 lanes=3 ring=0 metres=481`、`lanes=4 ring=0 metres=222`，证实收到车道时即使倒计时不工作仍走显示路径。原始过滤日志在 `output/highway-guidance/simulation-serial.log`。本次串口窗口未观察到 >500 米车道。2026-11-02，用户在 Build24／175c.8 按高速模拟验收问题回复“手机和圆屏都能显示”，确认本次手机提示和圆屏车道显示修复。该结果为用户实屏确认；并非新增 >500 米串口测量，也不代表所有高速路段均有 SDK 数据。
- 路口放大图仅接入手机；圆屏仍显示车道箭头，不新增放大图蓝牙传输。
- 原有 4bit 车道协议仅能表达已有方向码 0–14，SDK 的 16–23 扩展车道组合在圆屏上仍有既有限制；手机官方图片不受该编码限制。本轮未新增对扩展组合的近似映射，也不扩展协议。

## 地图“改善不明显”的核查

- 建筑本来就是二维语义掩码，圆屏没有楼高、侧面或 3D 模型，换成所谓二维模型不会自动改善当前结果。
- 175c.7/本轮 175c.8 的颜色采样抗锯齿均默认关闭。此前实际 ESP32 合成测量为 34.191 → 73.136 ms，超出 10% 预算，因此不能把诊断 AA 效果当作已交付的默认效果。
- Build23 的手机拓扑清理用于新采集分类图；旧完整地图包仍作为有效缓存直接复用，不会因升级强制重采。没有新的采集时，旧道路和建筑外观不会随 App 更新改变。本轮没有清除用户离线包或强行刷新。
- 保留源图中已有道路窄缝可以改善平行路粘连，不能恢复源图已合并的高架/地面层级。真正全图道路上下层分隔仍未实现；公开数据调查结果见 `map-smoothing-research.md`。
- 后续若要明显改善视觉，需要继续优化抗锯齿成本并处理旧图的渐进更新；本轮未把原始地图细节丢失或真实分层问题宣称为已修复。
