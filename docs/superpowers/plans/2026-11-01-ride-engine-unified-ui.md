# 自行车导航引擎升级与三模式统一UI方案

## 目标与已确定的取舍

将普通自行车导航升级到高德官方 `AMapNaviRideManager`，由SDK承担定位匹配、转向引导、偏航重算和到达判断。驾车、摩托车、自行车继续共用统一规划入口与App导航界面。

已确认的产品规则：

- **普通自行车路线默认使用官方引擎**；失败时明确提示，用户可选择现有兼容引擎，不静默切换。
- **自行车分享默认保留原轨迹**，沿用现有独立导航；规划页另提供“用官方引擎重新规划”，展示原线与新方案后再开始。
- **三种导航采用地图优先布局**，参考[上游iOS界面](https://github.com/zyn950929/MotoNav/tree/c67c0781f2b02c79c9724fd0f75ee474f2a54bbd/ios/MotoNav)，保留统一操作方式。
- 摩托车普通规划继续使用网页方案；摩托车分享继续采用你确定的驾车SDK策略。

## 引擎与数据流

### 1. 先统一管理SDK实例

新增轻量的 `NavigationCoordinator`，集中管理驾车、骑行SDK实例及会话代次，不另建通用插件框架。

- 当前SDK版本已经要求驾车与骑行单例互斥。切换顺序固定为：失效旧回调 → 停止导航和相关任务 → 解绑地图、delegate和数据代表 → 释放引用 → 确认销毁成功 → 创建目标引擎。[官方互斥说明](https://lbs.amap.com/api/ios-navi-sdk/changelog)
- 销毁失败时不创建另一个SDK实例，提示重试或使用兼容导航。
- 移除应用启动时无条件创建驾车引擎的行为。分享重算、静态电子眼查询、地图解绑和Key重建统一遵守实例所有权；迟到回调或地图销毁操作不得重新创建旧单例。
- 所有“正在导航”判断覆盖驾车、官方骑行和独立导航，防止更换目的地、巡航或导入分享抢占当前导航。

### 2. 接入官方骑行桥接层

新增 `RideBridge`，提供规划、选择路线、开始真实/模拟导航、暂停/继续、调整模拟速度、停止，以及导航状态和路线选项。

- 使用现有SDK的**无途经点独立骑行算路接口**，策略为多路线默认值；保存返回的 `AMapNaviRouteGroup`，预览、选路及开始导航都使用同一组结果。
- 每次规划绑定独立请求代次；25秒超时，取消或过期结果不得覆盖新输入。接受SDK实际返回的路线数量，不强求多条。
- 采用现有回调隔离方式，复用 `ArrivalPolicy`。导航中由SDK负责偏航重算，不叠加旧引擎的偏航计数和路线跟踪。
- 重算失败时保留当前路线与导航，提供重试；不在途中自动切换引擎。改用兼容模式需退出当前导航、从真实当前位置重新规划并预览。
- 沿用现有语音服务并关闭SDK内置播报，避免重复播报；保留静音、音乐压低和耳机输出。

### 3. 对接现有数据与圆屏

扩展规划器的实际后端标识为 `driveSDK / rideSDK / independent`，出行方式与实际引擎分别记录，避免“摩托车分享使用驾车SDK”等情况被错误判断。

- 官方骑行回调转换为现有导航读数与BLE消息，继续输出转向、距离、道路文字、速度、剩余里程、ETA、GPS状态和到达事件；不修改ESP32通信协议。
- SDK匹配位置用于导航；手机定位继续用于真实当前位置和轨迹记录，骑行定位活动类型设为 `.fitness`。模拟位置始终独立，结束后立即恢复真实位置来源。
- 真实导航记录轨迹，模拟导航不记录。历史记录继续保存规划输入，恢复时重新算路，不保存或伪造可长期复用的SDK路线ID。
- 路线变化时更新沿线地图；蓝牙重连同步当前会话。锁屏后沿用现有沿线缓存策略，不依赖后台GPU截图。

## 三种导航的UI设计

复用现有 `AppTheme` 和共享导航浮层，参考上游的系统蓝、语义色、紧凑HUD与玻璃控制栏。

- **顶部单张紧凑卡片**：方向图标、下次动作与距离、道路名、ETA和剩余信息。弱定位、重算等状态使用简短状态条。
- **底部轻量控制栏**：速度、全览/跟随、静音、隧道快捷操作和更多；保留独立的长按结束操作。模拟控制、返回设置及完整SDK提示放入更多菜单。
- 驾车使用对应Drive地图，官方自行车使用Ride地图，网页/分享兼容导航保留现有地图；浮层布局、按钮语义和到达页面保持一致。
- 官方驾车及骑行保留对应的完整SDK界面切换入口。网页导航不显示无法提供的功能；缺失数据显示“—”或真实状态，不填充虚构提示。
- 按实测卡片高度设置地图可视区域，覆盖横屏、安全区、动态字号和VoiceOver。返回设置不停止导航，到达展示仍保留4秒。

## 实施顺序与验收

## Task 1: 打通最小官方骑行链路

先完成实例互斥、基础算路、选路和模拟导航，用现有界面验证当前SDK与手机Key。明确区分权限错误、网络问题和实现错误；基础能力未验证通过，不以兼容模式运行冒充升级成功。

依据（实现细节遵循上文"引擎与数据流"第1、2节）：NavigationCoordinator 实例互斥与销毁顺序、移除启动时无条件创建驾车引擎、RideBridge 无途经点算路/选路/模拟导航、25秒超时与请求代次、回调隔离复用 ArrivalPolicy、关闭SDK内置播报。

## Task 2: 接入完整导航与兼容分流

完成真实导航、偏航、语音、轨迹、圆屏和后台处理；接通普通路线、分享原线、历史恢复及显式回退。

依据（"引擎与数据流"第3节）：后端标识扩展为 driveSDK/rideSDK/independent、骑行回调转现有导航读数与BLE消息（不改ESP32协议）、SDK匹配位置用于导航而手机定位用于真实位置与轨迹、`.fitness` 活动类型、模拟位置独立且结束立即恢复、真实导航记轨迹模拟不记、历史只存输入、蓝牙重连同步会话、锁屏沿用沿线缓存。

## Task 3: 完成统一UI

调整共享浮层和三种地图容器，保留驾车完整提示、隧道操作及原有导航能力。

依据（"三种导航的UI设计"节）：地图优先布局、顶部单张紧凑卡片、底部轻量控制栏、Drive/Ride/现有地图三容器、浮层语义与到达页一致、官方SDK完整界面切换入口保留、缺失数据显示"—"、按实测卡片高度设地图可视区域、横屏/安全区/动态字号/VoiceOver、返回设置不停止导航、到达展示保留4秒。

## Task 4: 自动化回归

覆盖SDK切换与销毁失败、旧回调晚到、连续改变起终点、算路超时、路线选择一致性、重算失败保留原线、重复到达、模拟结束恢复GPS。验证自行车BLE消息、单位和坐标转换，并继续运行现有规划、到达、定位、隧道、地图和轨迹测试。

## Task 5: iPhone与圆屏验收

完成驾车→自行车→摩托车→自行车至少10轮切换；验证真实骑行、停车、偏航、弱GPS、断网恢复、模拟暂停/退出和分享原线。锁屏不少于20分钟检查定位、播报、轨迹及蓝牙；连接圆屏验证显示和断连重连。

（Ledger 裁定：圆屏未到货、实车骑行不可由 agent 执行——iPhone 侧可自动化项完成后，圆屏联测与实车路测记为 deferred-user-validation 并在交付说明中显式列出。）

## Task 6: 交付测试版

从Build14递增构建号，沿用原签名和Bundle ID覆盖安装，保留Key、设置及历史。记录验证结果；正式替代旧自行车引擎须另行决定，本轮保留兼容路径。

## 边界与默认值

- 仅开发iOS；保持当前 `AMapNavi 10.1.600`、`AMapSearch 9.7.5`，本轮不同时升级依赖或合并其他平台更新。
- 自行车本轮仍不接入收费途经点能力；输入中有途经点时明确提示，不静默丢弃。保留现有模拟速度选择。
- 自动隧道调光继续限定于驾车SDK路径，自行车保留手动操作；自行车红绿灯读秒不列入本轮承诺。
- UI沿用已有来源说明；Key、Cookie和精确位置不进入新增诊断输出。

当前已完成代码和接口核对，官方骑行的实际Key权限、后台表现及实体圆屏效果尚未验证，必须通过上述真机验收后才能标记完成。
